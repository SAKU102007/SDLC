## 1. Введение

### 1.1 Назначение документа
Настоящий документ описывает архитектурный и системный дизайн веб-приложения «LabReportValidator». Он служит техническим руководством для разработчиков и инженеров по тестированию, связывая требования SRS со структурой кода, базой данных и алгоритмами проверки.

### 1.2 Область применения
Система автоматизирует приём, структурную валидацию и проверку на плагиат студенческих отчётов по лабораторным работам, а также предоставляет преподавателю инструменты контроля сдачи и аналитики.

### 1.3 Определения, акронимы и сокращения
* **SDD** — Software Design Description.
* **SRS** — Software Requirements Specification.
* **ADR** — Architecture Decision Record.
* **Шингл (Shingle)** — последовательность из k последовательных слов нормализованного текста, используемая для сопоставления заимствований.
* **Категории статусов** — группы состояний жизненного цикла отчёта (Обработка, Шаблон, Антиплагиат, Рецензирование).

### 1.4 Ссылки
* Спецификация требований к ПО: `docs/srs/srs.md`.
* Стандарт описания архитектуры: ISO/IEC/IEEE 42010:2011.
* Протоколы архитектурных решений: `adr/0001-*.md`, `adr/0002-*.md`, `adr/0003-*.md`.

## 2. Обзор дизайна

### 2.1 Задачи стейкхолдеров
* **Студент:** быстрая проверка отчёта (< 5 с на шаблон, < 15 с на плагиат), понятная причина отклонения работы при наличии замечаний.
* **Преподаватель:** оперативное получение информации об инцидентах плагиата (≥ 30 %), сводная таблица успеваемости групп.
* **Администратор:** управление справочниками предметов, шаблонами и учётными записями.
* **Разработчик / Архитектор:** слабая связанность сервисов, поддерживаемость, высокая производительность на базе PostgreSQL.

### 2.2 Выбранные точки зрения
Для полного описания архитектуры выбрано 8 проектных представлений, согласующихся с методикой кафедры ЭВМ БГУИР.

## 3. Проектные представления

### 3.1 Представление 001-context (Контекст)
Система функционирует как веб-приложение, доступное авторизованным пользователям (студенты, преподаватели, администраторы) через современные браузеры (Chrome, Firefox, Edge). Входными артефактами являются файлы отчётов в форматах PDF и DOCX объёмом до 10 МБ.

### 3.2 Представление 002-modules (Композиция и структура)
Архитектура представляет собой модульный монолит на ASP.NET Core 8 MVC:
* **WebUI:** контроллеры MVC, Razor Views, ViewModel.
* **AuthService:** аутентификация через ASP.NET Core Identity.
* **ReportService:** управление загрузкой, сохранением файлов на диске и версионностью.
* **ValidationService:** парсинг текста документов и контроль наличия 5 обязательных секций (титульный лист, цель работы, ход работы, выводы, приложение).
* **PlagiarismService:** глобальное сопоставление шинглов (k=4) со всеми отчётами в базе данных PostgreSQL.
* **NotificationService:** формирование оповещений преподавателям при превышении порога заимствования 30 %.
* **DataStorage (EF Core / Npgsql):** реляционное хранилище метаданных, хэшей и результатов.

Графическая схема структуры приведена на рисунке 3.1 (`sdd/images/labreport-structure.png`).

### 3.3 Представление 003-information (Информация)
Сущности предметной области:
* `User` (Id, Email, PasswordHash, FullName, Role, GroupNumber).
* `Subject` (Id, Title, Course, TeacherId).
* `LabWork` (Id, SubjectId, Number, Title, Deadline).
* `Report` (Id, LabWorkId, StudentId, CurrentVersion, Status, IsOverdue).
* `ReportVersion` (Id, ReportId, VersionNumber, FilePath, FileFormat, FileSize, UploadedAt).
* `ValidationResult` (Id, ReportVersionId, StatusCategory, FoundSections, MissingSections, Remarks).
* `PlagiarismMatch` (Id, ReportVersionId, SourceReportId, MatchPercentage, IsThresholdExceeded).
* `Notification` (Id, RecipientId, ReportId, Message, CreatedAt, IsRead).

Информационная модель представлена на рисунке 3.2 (`sdd/images/labreport-information.png`).

### 3.4 Представление 004-interface (Интерфейс)
Маршруты веб-приложения:
* `/Account/Login`, `/Account/Register` — авторизация и регистрация.
* `/Student/Labs` — список доступных лабораторных работ и статусов сдачи.
* `/Report/Upload/{labId}` — форма загрузки отчёта.
* `/Report/Results/{reportId}` — результаты валидации структуры и антиплагиата.
* `/Teacher/Dashboard`, `/Teacher/Review/{reportId}` — панель преподавателя и рецензирование.
* `/Admin/Subjects`, `/Admin/Templates` — управление дисциплинами и шаблонами.

### 3.5 Представление 005-validation (Взаимодействие и алгоритм)
Алгоритм обработки отчёта:
1. Загрузка файла, валидация формата (PDF/DOCX) и размера (≤ 10 МБ).
2. Извлечение текста (DocumentFormat.OpenXml для DOCX, PdfPig для PDF).
3. Поиск 5 обязательных разделов регулярными выражениями. Если разделы отсутствуют -> статус `StructureRejected`, выход из пайплайна.
4. Вычисление 4-словных шинглов текста.
5. SQL-запрос поиска совпадающих шинглов по всей таблице `ReportShingles` в PostgreSQL.
6. Вычисление максимального процента совпадения по формуле Жаккара.
7. Если `MatchPercentage >= 30%` -> статус `PlagiarismRejected`, возврат студенту на доработку, создание записи в `NotificationService` для преподавателя.
8. Если `MatchPercentage < 30%` и структура корректна -> статус `UnderReview` (допуск к проверке преподавателем).

Сценарий валидации представлен на рисунке 3.3 (`sdd/images/labreport-validation.png`).

### 3.6 Представление 006-states (Динамика состояний)
Модель жизненного цикла отчёта содержит 4 категории статусов:
1. **Категория «Обработка»:** `Uploaded` -> `Validating`.
2. **Категория «Шаблон»:** `StructureRejected` (при отсутствии обязательных секций).
3. **Категория «Антиплагиат»:** `PlagiarismRejected` (при совпадении ≥ 30 %).
4. **Категория «Рецензирование»:** `UnderReview` -> `RevisionRequired` / `Accepted` -> `Graded`.
* Модификатор `Overdue` устанавливается, если дата `UploadedAt > LabWork.Deadline`.

### 3.7 Представление 007-deployment (Развёртывание)
Клиентский браузер (Chrome, Firefox, Edge) взаимодействует по протоколу HTTPS с сервером ASP.NET Core 8 MVC (веб-сервер Kestrel). Сервер взаимодействует с СУБД PostgreSQL 16 через пул подключений TCP/IP (порт 5432). Схема развёртывания приведена на рисунке 3.4 (`sdd/images/labreport-deployment.png`).

### 3.8 Представление 008-quality (Ресурсы и качество)
* **Производительность:** индекс GIN на хэши шинглов гарантирует поиск заимствований за ≤ 1.5 с даже при базе в 10 000 отчётов.
* **Надёжность:** ACID-транзакции при сохранении версий и результатов проверок.
* **Безопасность:** хеширование паролей алгоритмом PBKDF2 (ASP.NET Identity), защита от XSS и CSRF (токены антиподделки), изоляция прав по ролям.

## 4. Архитектурные решения (ADR)
1. `ADR-001`: Серверный модульный монолит на ASP.NET Core 8 MVC.
2. `ADR-002`: Алгоритм шинглов (k=4) и инвертированный индекс PostgreSQL для проверки по глобальной базе отчётов (порог 30 %, возврат студенту, уведомление преподавателю).
3. `ADR-003`: Конечный автомат с 4 категориями статусов отчёта.
