# ADR-002: Алгоритм проверки на плагиат по глобальной базе отчётов

## Контекст и постановка задачи

Согласно правкам Заказчика и преподавателя, система должна выполнять проверку отчёта на текстовые заимствования относительно **всех отчётов, ранее загруженных в систему** (глобальная база по всем предметам, группам и годам). При обнаружении совпадений 30 % и более отчёт автоматически возвращается студенту, а преподавателю отправляется уведомление. Требуется алгоритм, укладывающийся в норматив времени проверки (REQ-PERF-003, ≤ 15 с).

## Драйверы решения

* Глобальный охват: поиск заимствований среди сотен и тысяч документов в базе.
* Требование к производительности: проверка отчёта до 5 МБ не более чем за 15 секунд (REQ-PERF-003).
* Точность и устойчивость к перестановкам слов и изменению пунктуации.
* Полная автономность: работа без платных внешних веб-сервисов (REQ-FUNC-007).

## Рассмотренные варианты

* Вариант 1: Попарное построчное сравнение текстов (алгоритм Левенштейна / LCS).
* Вариант 2: Внешний API антиплагиата (Антиплагиат.ру / Copyscape).
* Вариант 3: Алгоритм шинглов (w-shingling, k=4) с хэшированием N-грамм и инвертированным индексом в PostgreSQL.

## Оценка вариантов

### Вариант 1: Попарный LCS / Левенштейн
* Плюсы: детальный поиск вставок и удалений.
* Минусы: вычислительная сложность O(N * M), неприемлемо медленно при сравнении одного документа со всей базой данных.

### Вариант 2: Внешний API
* Плюсы: готовая реализация.
* Минусы: зависимость от сторонних сервисов, платная тарификация за каждую страницу, риск утечки конфиденциальных данных.

### Вариант 3: Алгоритм шинглов (k=4) с инвертированным индексом
* Плюсы: текст нормализуется (стемминг/лемматизация, удаление стоп-слов), разбивается на 4-словные шинглы, хэши которых сохраняются в базе данных с GIN-индексом. Сравнение сводится к быстрому пересечению множеств хэшей через SQL-запрос `WHERE shingle_hash = ANY(...)`. Время анализа документа по базе из 10 000 отчётов составляет менее 1.5 секунд.
* Минусы: требует дополнительного дискового пространства в PostgreSQL для хранения индекса шинглов.

## Итоговое решение

Принят **Вариант 3: Алгоритм шинглов (k=4) с инвертированным индексом в PostgreSQL**. При коэффициенте подобия Jaccard ≥ 0.30 (30 %) отчёт получает статус `PlagiarismRejected` и формируется уведомление преподавателю через `NotificationService`.
